💨 2. Pruebas de Humo (Smoke Testing)

2.1 Definición y Propósito

El Smoke Testing (también conocido como Build Verification Testing) es una suite rápida de pruebas superficiales cuyo propósito es responder a la pregunta: "¿El sistema está lo suficientemente estable como para ser probado en profundidad, o la compilación básica está rota?". Si una sola prueba de humo falla, el despliegue se detiene inmediatamente.

2.2 Casos de Prueba Ejecutados (tests/smoke.test.js)

ID Caso de Humo Verificación Técnica Resultado
SMK-01 Integridad de Archivos Críticos Verifica que index.html, styles.css, app.js, firebase-config.js y firebase-service.js existan y tengan contenido. ✅ Superado
SMK-02 Disponibilidad de Especialistas Comprueba que el catálogo semilla tenga al menos 2 médicos con licencia, especialidad y turnos. ✅ Superado
SMK-03 Presencia de Roles del Sistema Valida que existan usuarios configurados para los roles Admin, Medico y Paciente. ✅ Superado
SMK-04 Vitalidad de Autenticación Prueba el login de los 3 perfiles demo (admin@citas.local, ana@citas.local, maria@citas.local). ✅ Superado
SMK-05 Configuración de Firebase Cloud Valida la presencia de apiKey, projectId: "vitalis-care-f0e5e" y authDomain. ✅ Superado

🎯 3. Pruebas de Aceptación (Acceptance Testing / UAT)

3.1 Metodología BDD (Behavior-Driven Development)

Las Pruebas de Aceptación validan el software desde la perspectiva del usuario mediante historias estructuradas en:

  • Dado que (Given): Contexto inicial o precondición.
  • Cuando (When): Acción realizada por el actor.
  • Entonces (Then): Respuesta verificable esperada.

3.2 Historias de Usuario Evaluadas (tests/acceptance.test.js)

  • HU-01 [Paciente - Reserva Exitosa]: Dado un paciente autenticado y un especialista libre, cuando agenda un turno, el sistema crea la cita en estado Pendiente y descuenta la franja horaria. (✅ Aprobado)
  • HU-02 [Integridad Clínica - Anti-Solapamiento]: Si un médico ya tiene una cita de 10:00 a 11:00, cualquier intento de reserva de otro paciente en ese rango es rechazado automáticamente. (✅ Aprobado)
  • HU-03 [Médico - Ciclo de Atención]: El médico aprueba la cita pasando su estado a Confirmada y tras la atención la cierra en Completada. (✅ Aprobado)
  • HU-04 [Cancelación Aceptada > 24h]: Paciente solicita cancelar con 48h de anticipación → Cancelación exitosa y estado Cancelada. (✅ Aprobado)
  • HU-05 [Cancelación Rechazada < 24h]: Paciente intenta cancelar con solo 8 horas de antelación → El sistema rechaza la solicitud exigiendo la política de 24 horas. (✅ Aprobado)
  • HU-06 [Privacidad de Datos]: El paciente únicamente puede visualizar y consultar sus propias citas médicas. (✅ Aprobado)
  • HU-07 [Administrador - Métricas]: El tablero de control calcula con exactitud matemática el total de citas, pendientes, confirmadas y canceladas. (✅ Aprobado)

🕵️ 4. Pruebas Exploratorias (Exploratory Testing)

4.1 Metodología SBTM (Session-Based Test Management)

El testeo exploratorio investiga bordes, estrés, concurrencia y seguridad mediante Cartas de Prueba (Charters):

┌────────────────────────────────────────────────────────────────────────┐
│ CHARTER 1: Seguridad y Payloads Maliciosos                              │
│ • Exp-01: Inyección XSS en motivo de cita -> Sanitizado.                │
│ • Exp-02: Strings SQL ("DROP TABLE") -> Tratado como texto seguro.     │
│ • Exp-03: Textos masivos (50,000 chars) -> Truncado estricto a 500.   │
│ • Exp-04: Bytes nulos (\0) -> Purgados antes de guardar.               │
├────────────────────────────────────────────────────────────────────────┤
│ CHARTER 2: Límites Temporales (Boundary Values)                        │
│ • Exp-05: Cancelación con 24h y 1s de anticipación -> PERMITIDA.       │
│ • Exp-06: Cancelación con 23h 59m 59s -> RECHAZADA por política.       │
│ • Exp-07: Cruce de medianoche (23:30 a 00:30) -> Duración exacta 60m.  │
│ • Exp-08: Duración 0 segundos o fechas invertidas -> Invalidadas.     │
├────────────────────────────────────────────────────────────────────────┤
│ CHARTER 3: Concurrencia y Condición de Carrera (Race Conditions)       │
│ • Exp-09: Dos reservas asíncronas simultáneas en el mismo ms           │
│           -> Solo una es asignada; la otra se rechaza por colisión.    │
├────────────────────────────────────────────────────────────────────────┤
│ CHARTER 4: Fuzzing de Caracteres y Normalización                      │
│ • Exp-10: Nombres con tildes, diéresis y emojis ("Dr. Müller 🩺").     │
│ • Exp-11: Normalización de emails con espacios y mayúsculas.          │
│ • Exp-12: Contraseñas con alta entropía y símbolos especiales.         │
└────────────────────────────────────────────────────────────────────────┘

💻 5. Cómo Ejecutar las Pruebas

# Ejecutar las 63 pruebas consolidadas en PowerShell:
.\run-tests.ps1

# O mediante npm de manera individual:
npm run test:smoke        # Pruebas de Humo
npm run test:acceptance   # Pruebas de Aceptación (UAT)
npm run test:exploratory  # Pruebas Exploratorias
dotnet test               # Pruebas Backend C# xUnit
